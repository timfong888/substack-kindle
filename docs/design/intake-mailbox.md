# Design — Workspace intake mailbox, Gmail-native pass-through, swappable email store

> **Status:** Decided (2026-10-20) for the MVP. Supersedes the Resend proxy inbox in
> [`ingestion-rss-and-proxy-inbox.md`](ingestion-rss-and-proxy-inbox.md) as the ingestion path.
> Amends [`../requirements.md`](../requirements.md): Requirement 1 (ingestion), Requirement 13 (pass-through),
> the "Gmail path removed" note, and the Resend section (Resend is now send-only).
> Items marked **verify** are unconfirmed and must be checked before building on them.

## Decision in one paragraph

Each customer gets `substack+<code>@fong888.com`, a plus-address on one Google Workspace mailbox we own
(`substack@fong888.com`). The customer sets that address as their Substack account email. A daily job reads the
mailbox through a service account (our own mailbox, so no restricted-scope review), converts each newsletter to
Markdown, stores it with its header metadata in an **email store** behind a small Python interface (Convex for the
MVP; Supabase or Parquet later), then builds and sends the EPUB. Pass-through to the customer's real inbox is done by
**Gmail's own forwarding** so the customer receives the genuine newsletter, not a copy from us. Resend is used for one
thing: sending the EPUB to the Kindle.

## Why this and not the previous design

| Previous (Resend proxy inbox, decided 2026-10-10) | This design |
|---|---|
| Every newsletter costs two Resend emails (receive + forward); ~310/customer/month | Zero Resend emails for intake or forwarding; ~30/customer/month for digests |
| We forward "as" ourselves (`"<sender> via proxy" <kindle@mail.fong888.com>`); our domain's reputation carries the customer's login codes | Google forwards the original message with its DKIM intact and an ARC seal; `From` is the real publication |
| Webhook + retries + scheduler + stored bodies on Convex | One daily batch job; Gmail is the raw archive |
| Reactive dashboard re-reading full bodies (the cause of the Convex spending-limit incident) | Dashboard reads titles and dates only; bodies are batch data |

Why this is not the Gmail path that was removed on 2026-10-04: that path read the **customer's** mailbox with
`gmail.readonly`, a Google restricted scope requiring app verification and a CASA assessment. This design reads
**our** mailbox in **our** Workspace domain. An internal service account with domain-wide delegation needs no
verification and no customer OAuth.

## Observed facts (intake mailbox, 2026-10-19)

Checked with the Gmail API on `substack@fong888.com`, 201 messages in 14 days, all to `substack+tim@fong888.com`.

- Substack accepts a plus-address as the account email and delivers to it unchanged (`To` and `Delivered-To` keep
  the plus-tag).
- Every newsletter authenticates: `Authentication-Results: dkim=pass header.i=@mg-d1.substack.com … dmarc=pass
  (p=REJECT) header.from=substack.com`. Google evaluates this on receipt; we only read the header.
- Headers that identify the **account** (not the publication):
  - `X-Mailgun-Variables` JSON: `user_id` (the subscriber's Substack account id, stable across publications),
    plus `publication_id`, `post_id`, `subdomain`, `post_type` (`newsletter`), `post_audience`.
  - `X-Mailgun-Sid` (base64 JSON): `[sid, recipient address, …]`.
  - `Delivered-To`: the plus-address.
- Headers that identify the **publication**: `List-Id: <bytebytego.substack.com>`, `List-Url`, `List-Post` (the
  canonical post URL — the cross-channel identity key from the earlier design), `Feedback-Id: …:pub-<id>:substack`.
- Noise in the same mailbox: `From: Substack <no-reply@substack.com>` "Live video with … now" notices; account mail
  (login codes, receipts). Some newsletters land in `CATEGORY_PROMOTIONS`, so the job must not filter on Gmail
  category.

## Components

### 1. Addressing

- `code` is generated by the existing `proxyAddress.ts` generator (slug + 8 random chars), issued once per user and
  never changed. The owner's `tim` tag predates this and is acceptable for the MVP only.
- The address is `substack+<code>@fong888.com`. **verify**: Workspace "catch-all" is not needed; plus-addressing
  delivers to the base mailbox by default.

### 2. Accept rule (protects the forwarded mail and the digest)

A message is attributed to user `code` only when all of:

1. `Authentication-Results` (the one added by `mx.google.com`) contains `dmarc=pass` and `header.from=substack.com`.
2. `Delivered-To` equals `substack+<code>@fong888.com` for a known code.
3. The Substack `user_id` in `X-Mailgun-Variables` equals the id **pinned** to that code. The pin is set on the first
   accepted message for the code and never changes automatically. A mismatch is stored as `kind: "rejected"` with
   metadata only and surfaced on the dashboard.

Rule 3 means that knowing a user's plus-address is not enough to put content into their digest: the sender's own
Substack account id would not match. Everything from `no-reply@substack.com`, or with `post_type` other than
`newsletter`, is stored as `kind: "notification"` or `kind: "account"` (metadata only, no body) and never enters an
EPUB.

### 3. Pass-through (Gmail-native forwarding)

Done once per user at onboarding, by the service account acting on `substack@fong888.com`:

1. `users.settings.forwardingAddresses.create` with the customer's real address. Google emails a verification link
   to that address; the customer clicks it. This doubles as proof that the customer owns the address.
2. `users.settings.filters.create` with criteria `deliveredto:substack+<code>@fong888.com` and action `forward` to
   the verified address. (`deliveredto:` is exact; `to:` would also match CC.)

Properties: the customer receives the original message (original `From`, Substack DKIM, Google ARC); no Resend
volume; no deliverability risk on our domain. Known limit: Gmail does not forward messages it classifies as spam.
Cancellation: delete the filter; the 90-day account-mail grace period from the earlier design becomes "keep the
filter for 90 days, then delete it".

Scopes for the service account, all delegated only to `substack@fong888.com`: `gmail.readonly`, `gmail.modify`
(labels), `gmail.settings.basic`, `gmail.settings.sharing` (forwarding addresses).

### 4. Ingest job (`ingest_run.py`, daily, GitHub Actions — SAT-1105)

1. List messages **without** label `kindle/stored` (the label is the cursor; no timestamps to get wrong).
2. Fetch each in `full` format. Parse headers: `From`, `To`, `Delivered-To`, `Subject`, `Date`, `Message-ID`,
   `List-Id`, `List-Post`, `List-Unsubscribe`, `Authentication-Results`, `X-Mailgun-Variables`; Gmail `internalDate`
   and label ids.
3. Apply the accept rule → `kind` ∈ `newsletter | notification | account | rejected`.
4. For `newsletter`: HTML → Markdown with the existing deterministic parser (`parsing.py` + `substack_clean.py`).
   No LLM (Req 8/15).
5. `store.put(email)`; then add the label. Idempotent on the Gmail message id: a crash between put and label
   re-puts harmlessly.
6. Logs: counts and ids only. The repo is public and Actions logs are public.

Authentication from GitHub Actions: **Workload Identity Federation** to the service account, so no long-lived key
exists anywhere. **verify** the WIF setup against current Google docs before building.

### 5. Email store (swappable)

The Python pipeline depends on this interface and nothing else:

```python
class EmailStore(Protocol):
    def exists(self, gmail_message_id: str) -> bool: ...
    def put(self, email: StoredEmail) -> None: ...
    def delivery_targets(self) -> list[DeliveryTarget]: ...      # (user_code, kindle_email)
    def undelivered(self, user_code: str, *, since: datetime, until: datetime) -> list[StoredEmail]: ...
    def mark_delivered(self, ids: list[str], *, delivered_at: datetime) -> None: ...
    def purge_bodies_older_than(self, cutoff: datetime) -> int: ...
```

`StoredEmail` fields: `user_code, gmail_message_id, message_id, from_address, from_name, publication
(List-Id), post_url (List-Post), subject, received_at, kind, substack_user_id, markdown (newsletter only),
markdown_bytes, stored_at, delivered_at`.

Backends:

| Backend | When | Notes |
|---|---|---|
| **Convex** (MVP) | now | Users and Clerk auth already live here. One `emails` table; indexes `byGmailMessageId`, `byUserAndReceivedAt`, `byUserKindAndDeliveredAt`. Python calls HMAC-guarded HTTP functions (the existing `pipeline.ts` pattern). Markdown is 20–100 KB, under the 1 MiB document cap. |
| Supabase | if SQL/full-text querying becomes a feature | Same interface over `psycopg`; Postgres full-text on `markdown`. |
| Parquet + DuckDB | if cost must be ~$0 and queries are batch-only | One Parquet file per day in object storage (R2/S3); DuckDB reads them directly from Python. No server. |

Convex is used as a document store here, not as a reactive database. The dashboard queries return titles, dates and
`kind` only; it never subscribes to bodies. With the Resend inbox gone, the Convex **Starter** tier should cover the
MVP (**verify** against usage after one week).

Retention: Gmail is the raw archive. The store keeps Markdown for 30 days after delivery, then
`purge_bodies_older_than` drops bodies and keeps metadata.

### 6. Digest job (`digest_run.py`, daily, after ingest)

For each `delivery_targets()` entry: `undelivered(window)` → build one EPUB (`job_epub`) → `resend.send_epub` with
`Idempotency-Key = digest-<code>-<window>` → `mark_delivered`. One user failing must not stop the others.

|---|---|---|
| Resend emails | ~310 | ~30 |
| Convex | Pro seat + reactive reads | Starter likely; ~200 documents, ~10 MB |
| Google Workspace | — | one mailbox (already owned) |
| Compute | Convex actions + scheduler | GitHub Actions, ~3 min/day, $0 |

## Owner setup (one-time)

Google Cloud (project for substack-kindle):
1. Create a service account `substack-intake`.
2. Google Admin console → Security → Access and data control → API controls → **Domain-wide delegation** → add the
   service account's client id with the four Gmail scopes above.
3. Set up Workload Identity Federation for the GitHub repo `timfong888/substack-kindle` and grant the pool
   `roles/iam.workloadIdentityUser` on the service account.

GitHub (repo secrets): `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT`, `CONVEX_URL`,
`PIPELINE_SHARED_SECRET`, `RESEND_API_KEY`, `WHITELIST_EMAIL`. No per-user values.

Exact click paths are written into the implementing ticket (SAT-1104) when each step is reached.

## Out of scope

- Non-Substack newsletters (the accept rule is Substack-specific by design; a second rule set is a later ticket).
- RSS ingestion for free publications (still available; not needed when the proxy address receives everything).
- Per-user schedule preferences.
